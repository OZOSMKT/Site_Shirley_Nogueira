# Shirley Dermatologia — Design Specification

**Versão:** 0.1

Este documento é a fonte principal de verdade para a direção visual, estrutura, conteúdo e comportamento do site da Dra. Shirley Nogueira.

---

## 01. Visão do projeto

Landing page institucional da Dra. Shirley Nogueira, com foco em:

- autoridade médica;
- experiência;
- tecnologia;
- sofisticação;
- cuidado;
- exclusividade;
- naturalidade;
- confiança.

### Conceito visual

> **Minimalismo sofisticado + luxo discreto + estética editorial + autoridade médica.**

A referência estética não deve ser copiada como template. O objetivo é absorver princípios de refinamento e traduzi-los para uma identidade própria.

---

## 02. Princípio criativo

> **A arquitetura do projeto deve ser preservada, mas sua execução visual pode evoluir.**

O Claude pode melhorar:

- composição;
- proporção;
- espaçamento;
- tipografia;
- responsividade;
- tratamento das imagens;
- interações;
- animações;
- microinterações;
- hierarquia visual.

### Não alterar sem autorização

- quantidade de seções;
- ordem das seções;
- função narrativa das seções;
- conteúdos factuais;
- imagens explicitamente definidas como obrigatórias.

> **Não seja criativo com a arquitetura. Seja criativo com a execução.**

---

## 03. Arquitetura da página

A página deve seguir esta sequência:

1. **Hero**
2. **Sobre a Dra. Shirley**
3. **Precisão / segunda fotografia**
4. **Tecnologias**
5. **Conhecimento / Excelência**
6. **Entre em contato**
7. **Footer**

Não criar novas seções nem remover estas seções sem autorização.

# 04. Identidade visual

## Tipografia

### Antonio — primária

Usar principalmente em:

- títulos;
- palavras de impacto;
- números;
- nomes de tecnologias;
- elementos editoriais;
- grandes chamadas.

### Montserrat — secundária

Usar principalmente em:

- textos;
- descrições;
- navegação;
- botões;
- informações;
- labels;
- elementos funcionais.

A combinação **Antonio + Montserrat** é uma característica fundamental da identidade e pode ser explorada dentro de uma mesma headline.

# 05. Paleta

| Função | Cor |
|---|---|
| Fundo claro principal | `#F5EADD` |
| Marrom institucional | `#3C2E23` |
| Dourado | `#D0A568` |
| Taupe | `#B7A084` |
| Marrom médio | `#6B513C` |
| Branco | `#FAFAFA` |
| Preto | `#000006` |

### Regras

O dourado deve ser utilizado como **acento**, não como cor dominante.

Evitar excesso de:

- dourado;
- gradientes;
- brilho;
- glow.

Equilíbrio visual aproximado:

- **60%** tons claros / espaço negativo;
- **30%** marrom / fotografia / elementos escuros;
- **10%** dourado / detalhes.

Esses valores são uma orientação estética, não uma regra matemática.

---

# 06. Linguagem premium

O site não deve tentar provar que é premium.

### Evitar

- aparência de template de clínica;
- luxury aesthetic exagerada;
- gradientes chamativos;
- glow;
- glassmorphism excessivo;
- sombras pesadas;
- excesso de elementos decorativos;
- animações chamativas;
- excesso de bordas arredondadas;
- aparência de ecommerce.

### Priorizar

- espaço negativo;
- fotografia;
- tipografia;
- proporção;
- composição;
- alinhamento;
- ritmo;
- detalhes discretos;
- consistência.

> **Premium = qualidade da execução, não quantidade de efeitos.**

---

# 07. Header

O header deve:

- permanecer visível durante o scroll;
- acompanhar a página;
- utilizar efeito de blur;
- possuir transparência controlada;
- ter aparência elegante e discreta.

### Desktop

Logo + navegação para:

- Home;
- Sobre;
- Tecnologias;
- Contato.

### Mobile

Logo + menu compacto/hamburger.

### Blur

Utilizar:

- background semitransparente;
- `backdrop-filter: blur(...)`;
- contraste adequado.

Não transformar o header em glassmorphism exagerado.

### Scroll

Pode haver mudanças sutis de:

- opacidade;
- sombra;
- altura.

- CTA.

# 13. Assets dos equipamentos

Os equipamentos fornecidos são PNGs com transparência.

Utilizar os assets oficiais.

Não é obrigatório utilizar os backgrounds fotográficos atuais do Figma.

### Regra fundamental

Os equipamentos possuem proporções diferentes.

Não forçar todos a terem a mesma escala.

Os cards devem possuir dimensões consistentes, enquanto cada aparelho deve ser individualmente dimensionado para obter **peso visual semelhante**.

Preservar:

- proporções;
- transparência;
- qualidade;
- enquadramento.

É permitido criar/refinar:

- fundo;
- iluminação;
- sombra;
- composição;
- espaço interno.

> **Mesmo peso visual, não necessariamente o mesmo tamanho físico.**

---

# 14. Cards de tecnologia

Os cards devem utilizar uma linguagem inspirada no comportamento interativo da referência fornecida pelo cliente, **sem copiar seu design visual**.

### Estado inicial

Apresentar de forma minimalista:

- número;
- equipamento;
- nome;
- informação curta.

### Hover

O conteúdo deve se expandir/revelar progressivamente.

A expansão deve parecer integrada ao próprio card.

Não utilizar tooltip.

Não utilizar pop-up.

### Conteúdo revelado

Pode revelar:

- informação adicional;
- descrição da tecnologia;
- ação **SAIBA MAIS**.

### Touch

Como hover não existe em dispositivos touch, criar uma interação equivalente por toque.

### Estética

- elegante;
- editorial;
- minimalista;
- transição suave;
- sem efeitos exagerados.

# 18. Fotografia

Fotografias oficiais fornecidas no projeto devem ser priorizadas.

Não substituir imagens definidas como obrigatórias.

Pode ajustar:

- crop;
- escala;
- enquadramento;
- `object-position`;
- máscaras;
- bordas;
- sombra;
- composição.

Não:

- distorcer;
- aplicar filtros que alterem significativamente a aparência;
- criar tratamentos artificiais excessivos.

A fotografia deve transmitir:

> **profissionalismo + naturalidade + autoridade.**

---

# 19. Animações

Regra:

> **Se a animação chama mais atenção que o conteúdo, ela está exagerada.**

Priorizar:

- fade;
- reveal;
- deslocamentos pequenos;
- transições suaves;
- hover refinado;
- carrossel fluido.

Evitar:

- bounce;
- elastic;
- zoom excessivo;
- parallax exagerado;
- elementos girando;
- transições rápidas ou chamativas.

Respeitar:

`prefers-reduced-motion`.

# 22. Consistência

> **Consistência não significa repetição.**

Cada seção pode possuir uma composição diferente.

Todas devem compartilhar:

- mesma paleta;
- mesma tipografia;
- mesmo sistema de espaçamento;
- mesma linguagem fotográfica;
- mesmos princípios de bordas;
- mesma lógica de sombras;
- mesma delicadeza nas interações.

O resultado deve parecer **um único projeto**, e não sete layouts independentes.

# 23. Stack e organização técnica

O projeto deve utilizar uma stack moderna, organizada e adequada para deploy na Vercel.

### Preferência

**Next.js + TypeScript** são opções preferenciais, especialmente por integrarem bem com a Vercel.

Entretanto, o Claude possui autonomia para escolher uma alternativa tecnicamente superior quando houver justificativa.

### Código

Priorizar:

- TypeScript;
- componentes reutilizáveis;
- estrutura de pastas clara;
- separação entre componentes, dados, estilos e assets;
- código fácil de manter;
- nomes de arquivos e componentes claros;
- ausência de duplicação desnecessária.

Evitar:

- arquivos gigantes;
- componentes monolíticos;
- código repetido;
- dependências desnecessárias.

### Organização sugerida

```text
src/
├── app/
├── components/
│   ├── layout/
│   ├── sections/
│   ├── technologies/
│   └── ui/
├── data/
├── lib/
└── styles/

public/
├── images/
├── fonts/
└── icons/
```

A estrutura final pode ser diferente se houver uma solução melhor, desde que seja lógica e fácil de manter.

### Dados das tecnologias

Sempre que fizer sentido, manter os dados das 7 tecnologias separados da apresentação visual.

Exemplo:

```text
data/technologies.ts
```

Assim alterações de conteúdo não exigem modificar a estrutura visual do componente.

# 24. GitHub + Vercel + Deploy

O fluxo de publicação será:

> **Desenvolvimento → GitHub → Vercel**

O projeto deve ser preparado para versionamento desde o início.

### Não versionar

- `node_modules/`;
- `.env`;
- `.env.local`;
- credenciais;
- chaves privadas;
- caches;
- arquivos temporários;
- arquivos gerados desnecessariamente.

### README

O projeto deve possuir um `README.md` profissional e específico, contendo:

- descrição do projeto;
- tecnologias realmente utilizadas;
- estrutura do projeto;
- instalação;
- desenvolvimento local;
- build;
- deploy na Vercel;
- variáveis de ambiente, se houver;
- manutenção.

Não utilizar um README genérico gerado automaticamente pelo framework.

### Git

A branch `main` pode representar produção.

Commits devem ser claros e podem ser escritos **em português**.

Exemplos:

```text
feat: implementar carrossel de tecnologias
feat: adicionar header responsivo
style: refinar composição do hero
style: ajustar cards de tecnologia
fix: corrigir cards no mobile
docs: atualizar README
```

Não criar histórico artificialmente grande apenas para parecer profissional.

### Vercel

O projeto deve estar pronto para:

> **GitHub → Vercel → deploy automático**

Garantir compatibilidade com o ambiente da Vercel.

Antes de considerar o projeto concluído, validar:

- instalação limpa;
- build de produção;
- TypeScript;
- lint, se configurado;
- assets;
- fontes;
- rotas;
- links;
- carrossel;
- responsividade.

Objetivo:

> **clonar → instalar → executar → funcionar**

sem depender de configurações específicas da máquina do desenvolvedor.
